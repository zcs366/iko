## 1. 技术栈选型推荐

### 1.1 选型哲学

```
一人团队的技术栈选型原则（按优先级排序）：

1. 上下文连续性 > 性能          — AI需要"看到"全部对话历史
2. 可演进性 > 当下完美          — MVP不是最终形态，重构是常态
3. 集成密度 > 最佳组合          — 少一个集成点，少一次debug
4. 久经考验 > 最新最热          — 一人没有时间填坑
5. LLM编排 > 传统API            — 所有接口优先考虑LLM原生交互
```

### 1.2 完整技术栈（MVP推荐）

| 层 | 推荐方案 | 备选 | 理由（一人视角） |
|---|---|---|---|
| **后端框架** | Python FastAPI + Pydantic v2 | Node.js Hono, Go Fiber | FastAPI在MVP阶段可同时做REST + WebSocket + SSE，一人覆盖前后端桥接；Pydantic v2提供天然JSON Schema -> 自动生成OpenAPI -> LLM可直接读API文档调接口 |
| **前端框架** | Next.js 14 (App Router) | Nuxt 3, SvelteKit | 一人不用分别写前端/后端：Next.js Server Components + API Routes = 前端后整合在一个repo；Server Actions让表单/POST在组件里直接调逻辑，省掉一层API胶水。Vercel一键部署 |
| **数据库** | PostgreSQL (Supabase) | SQLite (Turso), Neon | 一人不需要运维。Supabase提供：①PostgreSQL ②Auth ③Realtime ④Storage ⑤Edge Functions。五个服务一个平台，减少集成点 |
| **ORM/查询** | Drizzle ORM | Prisma, SQLAlchemy | 类型安全（TypeScript/Go-style）、schema定义即文档、migration零心智。比Prisma轻，一人不需要图形化工具 |
| **向量数据库** | pgvector | Qdrant (自托管), Chroma | 不要独立部署向量库！pgvector在PostgreSQL里。一人不需要两个数据库。MVP阶段不建议自建Milvus/Weaviate |
| **AI/LLM编排** | LangChain (轻量使用) / 自写编排 | Vercel AI SDK, LlamaIndex | Vercel AI SDK + Next.js = 流式回复原生支持。自写编排函数比LangChain抽象层更可控。关键：MVP阶段**不依赖**LangChain做业务编排，只用它做prompt模板化 |
| **LLM调用** | OpenAI API + Anthropic API | Groq(快速推理), DeepSeek(降本) | 主力用Claude（长上下文，iko需要持久对话记忆），快速推理用Groq，降本用DeepSeek。抽象一层LLMProvider，切换模型不改业务代码 |
| **前端UI** | Tailwind CSS + shadcn/ui | Ant Design, Radix | shadcn/ui = 复制不走样 + 全可定制。一人不需要学完整的component library API。Tailwind直接在HTML里写样式，省掉CSS文件管理 |
| **认证** | Supabase Auth | Clerk, Auth0 | Supabase Auth = PostgreSQL Row Level Security原生整合。一人不用写认证中间件 |
| **部署** | Vercel (前端+Edge) + Railway/Fly.io (后端) | Render, DigitalOcean App Platform | Vercel: Next.js + Serverless + Edge Functions 千人级免费。Railway: FastAPI容器化部署，免费额度够MVP。一人不需要Kubernetes |
| **监控** | Sentry (错误追踪) + OpenTelemetry + Axiom (日志) | Highlight, Datadog(太贵) | Sentry: 一人不需要主动看日志，报错自动告警。OpenTelemetry: 标准化trace，未来迁移不影响。Axiom: 结构化日志即查即用，不需要ELK |
| **持久上下文** | 自定义Memory Layer (PostgreSQL + 向量混合) | Mem0, MemGPT | MVP阶段自建：对话历史存pgvector，摘要用Claude生成的每周记忆胶囊。**不依赖**任何外部记忆服务——它是iko的核心哲学，不能让别人控制 |
| **WebSocket/SSE** | Server-Sent Events (SSE) | WebSocket (Socket.IO) | SSE：浏览器原生支持、断线重连、一人模型双工通信足够。WebSocket在MVPeer-to-peer场景下过重。FastAPI用 `StreamingResponse` 原生SSE |
| **定时任务** | Vercel Cron Jobs + inngest | Celery（太重） | Vercel Cron免费5个job/月够MVP。Inngest处理"记忆胶囊老化刷新"等带状态的异步任务 |
| **搜索** | Meilisearch (自托管) | Algolia, Typesense | Meilisearch: 一键docker启动，REST API一人5分钟集成。MVP不需要Elasticsearch |
| **文件存储** | Supabase Storage / R2 | AWS S3, Cloudflare R2 | R2: S3兼容 + 零出站费。Supabase Storage = 直接和Auth联动，前端上传无需后端签名 |

## 2. CLAUDE.md 模板

```markdown
# CLAUDE.md — iko 知识研究系统

## 项目身份

iko（爱祝/ai祝）是一个陪你走得道快乐的知识研究系统。
核心哲学：长编→定本，搜→写→劈，以乐为终。

## 技术栈概要

- **前端**：Next.js 14 (App Router) + Tailwind CSS + shadcn/ui
- **后端**：Python FastAPI + Pydantic v2（过渡期为纯Next.js Server Actions，后续拆出）
- **数据库**：PostgreSQL + pgvector（Supabase托管）
- **ORM**：Drizzle ORM (TS) / SQLAlchemy (Python)
- **AI**：Claude-3-opus (主力长文) + GPT-4o (快速推理) + Groq (低延迟)
- **部署**：Vercel (前端+Edge) + Railway (后端API)
- **监控**：Sentry + OpenTelemetry + Axiom
- **搜索**：Meilisearch（知识库全文搜索）

## 架构原则

1. **上下文连续性优先**：所有设计确保LLM能看到完整对话历史+记忆胶囊
2. **可演进架构**：MVP用单体+Server Actions，不引入Kafka/微服务/独立向量库
3. **LLM原生接口**：优先让LLM读OpenAPI文档调用，而非手写SDK胶水
4. **记忆即产品**：Memory Layer是iko的核心差异，不允许被外部服务控制
5. **以乐为终**：用户体验优先于技术完美。宁可返工不要过度工程

## 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 向量库 | pgvector（不独立部署） | 一人团队不要维护两个数据库 |
| 部署 | Vercel + Railway | 零运维，免费额度够MVP |
| 前端状态 | React Server Components + URL params | 不需要Redux/Zustand |
| AI编排 | 自写编排函数 | LangChain抽象层太高，一人可控 |
| 认证 | Supabase Auth | 和数据库安全策略原生整合 |
| 任务队列 | Vercel Cron + Inngest | Celery太重，SQLite不够 |

## 一人团队工程纪律

### 代码规范
- 所有AI生成的代码必须包含架构注释（/* 为何这样设计 */）
- 禁止"一次性代码"：每个函数/组件必须有明确的职责声明
- 数据库schema变更必须附带down migration
- API响应必须有统一格式：`{ok, data?, error?, meta?}`

### 记忆层规范
- 对话摘要每5轮写一次pgvector嵌入
- 记忆胶囊每周自动刷新新鲜度（fresh→warm→grey→cold）
- 前提变化（premise change）自动触发推送提醒
- 胶囊去重：同一天同一用户同话题不重复推送

### MVP阶段演进路径
- **Phase 0**（当前）：纯Next.js + AI SDK + 本地PostgreSQL
- **Phase 1**（用户<100）：接入Supabase + FastAPI后端拆出 + pgvector
- **Phase 2**（用户<1000）：Meilisearch + Sentry + Cron记忆刷新
- **Phase 3**（用户>1000）：评估是否需要独立向量库/缓存层/CDN

### 命名约定
- 前端组件：`PascalCase`，目录 `feature-name/`
- 后端路由：`/api/v1/{resource}`
- 数据库表：`snake_case`，`t_`前缀（如 `t_capsules`）
- 环境变量：`NEXT_PUBLIC_*`（前端），`IKO_*`（后端）

### 关键命令
```bash
# 本地开发
npm run dev              # Next.js前端
uvicorn api.main:app --reload  # FastAPI后端

# 数据库
npm run db:generate      # 生成migration
npm run db:migrate       # 执行migration
npm run db:push          # 推送到Supabase

# 部署
npm run build            # 构建
git push main            # Vercel自动部署

# 测试
npm run test             # 单元测试
npm run test:e2e         # E2E测试
```

### 问答

**Q: MVP阶段能用Tailwind吗？**
A: 可以，shadcn/ui无依赖，但自定义组件尽量用Tailwind utility classes，减少CSS文件。

**Q: 后端用FastAPI还是Next.js API Routes？**
A: Phase 0用Server Actions + API Routes（一人不需要两个服务）。当需要WebSocket/SSE/长任务时，拆出FastAPI。

**Q: 需要Kubernetes吗？**
A: 不需要。MVP阶段1000用户以内，Vercel + Railway扛得住。

**Q: 何时引入AI缓存？**
A: 当相同prompt+上下文组合出现频率>10次/天时，考虑用PostgreSQL做结果缓存（TTL按场景设定）。
```

### 3.2 核心数据流（一人工作流程）

```
用户输入一个研究问题
        │
        ▼
[(1) 搜阶段] ──> 调用 LLM Provider Orchestrator
        │           ├── 并行搜索：互联网 + 知识库(Meili) + 记忆胶囊(pgvector)
        │           ├── 结构化输出：面(facets) + 关键引用
        │           └── 写回 t_sessions + t_sources
        │
        ▼
[(2) 写阶段] ──> 流式SSE长编输出到前端
        │           ├── 用户实时阅读，可打断/点调整
        │           └── 完成后写入 t_sessions
        │
        ▼
[(3) 劈阶段] ──> 自动触发Critique Agent
        │           ├── 找漏洞、模糊词、缺视角
        │           ├── 生成 t_capsules（记忆胶囊）
        │           └── 嵌入pgvector供后续检索
        │
        ▼
   记忆持久化 ──> Memory Layer
                    ├── 对话摘要（每5轮）→ pgvector
                    ├── 记忆胶囊（每周刷新新鲜度）
                    ├── 前提变化检测 → 推送提醒
                    └── 胶囊老化策略：fresh→warm→grey→cold
```

### 3.3 组件职责说明

| 组件 | 职责 | 不做什么 |
|------|------|---------|
| **LLM Provider Orchestrator** | 统一入口管理所有AI调用，故障切换（Claude→GPT→Groq），token追踪 | 业务逻辑、搜索执行、数据库写入 |
| **搜 Agent** | 多路并行搜索(pinecone/GitHub/wiki/知识库)，结构化输出面(facets)和引用 | 编写可读文稿、批判性审读 |
| **写 Agent** | 将面(facets)组合成流畅长编，用类比/示例/画面写作 | 搜索新知识、批判已写内容 |
| **劈 Agent** | 严格审读：找漏洞、模糊词、缺视角，输出结构化的修改建议 | 不写新内容，不提供正面评价 |
| **Memory Layer** | 对话摘要嵌入、记忆胶囊管理、新鲜度刷新、前提检验、推送去重 | 不参与实时对话推理、不过滤用户输入 |
| **Push Engine** | 当新查询匹配到老化(freshness=grey/cold)胶囊时推送提醒 | 不修改胶囊内容、不干涉用户决策 |
| **Freshness Manager** | 按时间+前提变化自动计算新鲜度分数，执行老化/归档策略 | 不影响实时性能、不决定用户是否采纳 |

## 4. 技术陷阱预警

### 🚨 陷阱1：过早向量化

**症状**：MVP第一天就上RAG（检索增强生成），花两周调试chunk size、embedding model、reranker。

**为什么是一人陷阱**：一人团队的时间是最稀缺资源。MVP阶段的核心任务是验证"用户是否愿意用这个产品"，而不是"检索准确率比基准高5%"。

**正确的做法**：
- Phase 0：用 `LIKE` 搜索 + LLM记忆就够了（用户<50，对话轮流基本全在上下文窗口）
- Phase 1（用户<100）：pgvector + 最简embedding（不用reranker）
- Phase 2（用户<1000+）：再引入Meilisearch全文搜索 + 向量混合检索
- 永远不要在MVP阶段自建Elasticsearch或Milvus

**判断标准**：
```
如果用户的查询80%都能在当前对话的上下文窗口内直接回答 → 不需要向量化
如果用户反复问"我上周说的那个……" → 才需要记忆检索
如果用户需要精确匹配文档中的技术细节 → 才需要RAG
```

### 🚨 陷阱2：过度微服务

**症状**：MVP第一天就拆成 auth-service、search-service、capsule-service、ai-orchestrator，每个独立部署+独立数据库。

**为什么是一人陷阱**：
- 单体架构debug一次，微服务debug N次（网络、序列化、一致性、超时）
- 一人不可能同时维护5个服务+5个数据库+消息队列
- 每次跨服务调用的心智成本是单体函数调用的10倍

**正确的做法**：
- Phase 0：Next.js Server Actions + 本地PostgreSQL（一个进程）
- Phase 1：拆出FastAPI后端（两个服务），仍共用同一个数据库
- Phase 2（用户>1000）：才考虑将Memory Layer拆为独立服务
- 原则：**一个服务满足所有需求，直到明确证明它是瓶颈**

**架构演进路径**：
```
Phase 0: [Next.js + 本地PG] — 一个进程
Phase 1: [Next.js] + [FastAPI + PG/Supabase] — 两个服务，一个数据库
Phase 2: [Next.js] + [FastAPI] + [Memory Service + PG + Meili] — 三个服务
Phase 3: [Next.js] + [API Gateway] + [各服务独立] + [消息队列] — 微服务
```
**不要跳过Phase 0和Phase 1直接跳到Phase 3。**

### 🚨 陷阱3：Prompt不可复用

**症状**：prompt硬编码在代码里、散落在10个文件中、缺少版本管理、换模型时全部重写。

**为什么是一人陷阱**：一人写的prompt，一周后自己也看不懂参数的含义。等到用户反馈"最近的回答变差了"，你根本不知道是代码变了还是prompt变了还是模型变了。

**正确的做法**：
```
iko/
├── prompts/
│   ├── base/
│   │   ├── system-search.md         # 搜Agent系统提示词
│   │   ├── system-write.md          # 写Agent系统提示词
│   │   └── system-critique.md       # 劈Agent系统提示词
│   ├── templates/
│   │   ├── long-form-generation.md  # 长编生成模板
│   │   ├── capsule-summary.md       # 记忆胶囊摘要模板
│   │   └── premise-check.md         # 前提检验模板
│   ├── versions/                    # prompt版本历史
│   │   ├── v1.0/
│   │   └── v1.1/
│   └── prompt-manager.py            # prompt加载+变量注入+版本追踪
```

**关键纪律**：
```
1. 每个prompt文件必须包含元数据头部（version, model, date, author）
2. 禁止在业务代码中写超过5行的prompt字符串
3. prompt变更必须走git commit，commit message写清楚"为什么改"
4. 每个环境变量模板字符串用 {variable} 格式，避免f-string散落
5. 每次切换模型时，记录哪些prompt需要修改+为什么
```

### 🚨 陷阱4：安全盲区

**症状**：一人团队最容易忽略的四个安全漏洞。

**① 提示注入（Prompt Injection）**
```
❌ 错误做法：
  用户的输入直接拼接到system prompt中
  "你的任务是回答关于{user_input}的问题"

✅ 正确做法：
  - 用户输入放在user prompt中，隔离不可信的system prompt
  - 使用分隔符标记用户输入边界（<user_input>...</user_input>）
  - 对敏感操作增加二次确认（"你要删除所有胶囊，确认吗？"）
```

**② 数据泄露**
```
❌ 错误做法：
  - 一个用户能看到另一个用户的记忆胶囊
  - LLM输出的日志中包含完整的对话历史
  - 嵌入向量混存在同一个pgvector集合

✅ 正确做法：
  - Supabase Row Level Security：每个表加 tenant_id 列
  - 日志中脱敏用户输入（只保留元数据，不保留内容）
  - pgvector搜索时带 WHERE tenant_id = :id 条件
  - 所有API响应过滤敏感字段（password, api_key, email）
```

**③ API Key 泄露**
```
❌ 错误做法：
  - 前端直接调用 OpenAI/Anthropic API
  - .env.local 不小心提交到GitHub
  - 在日志中记录请求/响应中透传的API key

✅ 正确做法：
  - 所有AI调用通过后端代理（Server Actions或FastAPI）
  - 在项目根目录加 .env.example（非 .env.local）
  - .gitignore 包含 .env* 和 *.pem
  - 使用 git-secrets 或 pre-commit hook 检查密钥泄露
  - 日志中过滤所有 Authorization 和 x-api-key 头
```

**④ 速率限制（Rate Limiting）**
```
❌ 错误做法：
  - 用户提交后直接调用LLM，没有频率限制
  - 一个用户恶意循环调用导致API账单爆炸
  - 没有请求队列导致LLM连接数溢出

✅ 正确做法：
  - Server Actions 实现限流（Vercel自带或手写token bucket）
  - LLM调用设置max_tokens+max_requests_per_minute硬限制
  - 每个用户每天有调用配额（free tier在MVP阶段必要）
  - 实时监控API费用，设置月度预算警戒线
  - 异步队列处理非实时请求（记忆刷新、批量搜索）
```

## 5. 决策树：什么时候用什么

### 数据存储决策

```
用户数据需要持久化？
├── 是 ──> 需要搜索？
│          ├── 是 ──> 需要语义搜索（模糊匹配+多语言）？
│          │          ├── 是 ──> pgvector（MVP）
│          │          └── 否 ──> Meilisearch
│          └── 否 ──> PostgreSQL（Supabase）
└── 否 ──> 临时状态用什么？
           ├── 浏览器本地（localStorage/sessionStorage）
           └── URL search params（可分享状态）
```

### LLM调用决策

```
需要实时对话（用户等待）？
├── 是 ──> 需要超长上下文（>100K tokens）？
│          ├── 是 ──> Claude-3-Opus
│          └── 否 ──> GPT-4o（更快更便宜）
├── 否 ──> 可以异步处理？
│          ├── 是 ──> 排队调用 + SSE推送结果
│          └── 否 ──> Groq（最快推理，适合实时搜索总结）
└── 用户需要结构化输出（JSON/表格）？
           └── GPT-4o（function calling最稳定）或Claude（tools模式）
```

### 部署决策

```
MVP上线 → 用户<100人？
├── 前端：Vercel（免费）
├── 后端：Next.js Server Actions（Phase 0）/ Railway（Phase 1）
├── 数据库：Supabase Free Plan（500MB够用）
└── AI：OpenAI/Anthropic Pay-as-you-go

用户100-1000人？
├── 前端：Vercel Pro（$20/月）+ ISR缓存
├── 后端：Railway（$5-20/月）+ FastAPI
├── 数据库：Supabase Pro（$25/月，8GB）
├── 搜索：Meilisearch（单容器，$10/月VPS）
└── 监控：Sentry Free + Axiom Free

用户>1000人 → 每层独立优化
├── 前端：CDN + Edge Functions + 应用缓存
├── 后端：多实例 + 负载均衡
├── 向量：评估独立Qdrant
└── 任务：引入消息队列
```
